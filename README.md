# @sellgar/pagination

Общая курсорная пагинация Sellgar backend. Node 24+, PostgreSQL, TypeORM 1.x.

Запрос: `{ limit?: number, nextToken?: string, ...filters }`; default 50, maximum 100.
Ответ: `{ items: T[], meta: { limit, nextToken: string | null } }`.
COUNT не выполняется. Подсчёт количества не входит в списочный контракт или
в библиотеку; отдельные read models для него будут проектироваться независимо.
Отсутствие продолжения обозначается только `nextToken: null`.

`CursorQueryDto` — базовый DTO списочного endpoint. `offset` отклоняется.
`CursorMetaEntity` — общая валидируемая форма метаданных.

Сервис подключает `PaginationModule` рядом с настроенным `ConfigModule` и получает
`CursorPagination` через Nest DI. `PAGINATION_TOKEN_SECRET` обязателен: случайный
секрет минимум 32 байта из Secret окружения, одинаковый у реплик одного сервиса.
Не хранить ключ в ConfigMap/исходниках и не использовать публичный fallback.
Замена ключа инвалидирует выданные токены; клиент начинает загрузку заново.
Без Nest можно создать `new CursorPagination(secret)` явно.

`pagination.read(query, request, { scope, filters, order })` получает
отфильтрованный QueryBuilder без limit/offset, стабильный endpoint scope и
нормализованные фильтры без limit/nextToken. order задаётся кодом владельца;
последний ключ — первичный ключ корневой сущности. Nullable-ключи не поддерживаются.
Поисковый rank допускается как SQL expression с типом real.

Граница из нескольких ключей раскладывается на непересекающиеся ветви `UNION ALL`.
Каждая ветвь получает свои equality/range-предикаты и limit+1; общий ORDER/LIMIT
выбирает следующую пачку. Это сохраняет смешанные ASC/DESC и позволяет PostgreSQL
использовать индексные границы вместо фильтрации всех предыдущих строк через OR.
Обоснование: [GitLab keyset performance](https://docs.gitlab.com/development/database/keyset_pagination/#performance).

Библиотека читает limit+1 уникальных ключей корня, затем загружает только выбранные
агрегаты с relations. Она не обрезает строки JOIN и не читает всю коллекцию.
Даты и числовые ключи берутся как SQL text, сохраняя микросекунды/точность БД.

Токен подписан HMAC-SHA256; подпись сравнивается через timingSafeEqual до разбора
ключей и обращения к БД. Изменённые payload/подпись/контекст отклоняются как 400.
HMAC защищает целостность, не шифрует данные: секретные поля в токен не помещать.
В context.filters включать все ограничения области запроса, в том числе shop/owner.
Права доступа всегда проверяются SQL-предикатами заново, независимо от токена.

Токен — внутренний URL-safe continuation bookmark. Клиенты хранят и передают его
целиком; его схема не является публичным API и может меняться. Он связан с scope,
сортировкой и фильтрами, но не является credential и не заменяет auth-предикаты.
Токен не хранит SQL или предоставленные клиентом выражения сортировки.

Пагинация не фиксирует снимок коллекции между HTTP-запросами. Удаление граничной
записи не мешает продолжению; вставки до курсора не повторяют прошлую страницу.
Изменение ключа сортировки у существующей записи может переместить её; для обычных
списков следует выбирать неизменяемые created_at/uuid/code. При необходимости
согласованного чтения одной страницы caller использует свою транзакцию.

Индексы принадлежат сервису и создаются его миграциями. Индекс должен учитывать
типовые equality-фильтры и порядок, включая уникальный последний ключ и ASC/DESC.
Например, для магазина и `created_at DESC, uuid ASC` проверяется B-tree
`(shop_uuid, created_at DESC, uuid ASC)`. Это пример под конкретный запрос,
не универсальный индекс для всех комбинаций фильтров. При FTS rank вычисляется
для найденных строк: GIN не заменяет индекс сортировки и не обещает постоянное время.
Производительность проверять `EXPLAIN (ANALYZE, BUFFERS)` на глубоких курсорах
и сопоставимых объёмах. Одна замена OFFSET на WHERE не доказывает ускорение.

Контракт предназначен для последовательной догрузки. Произвольного номера страницы
нет. Сортировку задаёт сервер из своего разрешённого набора выражений; клиент не
передаёт SQL. Смена сортировки/фильтров требует начать список без nextToken.

При отдельном checkout используется Yarn 4 через Corepack; внутри сервиса — его Yarn workspace.
Проверки: `corepack yarn build && corepack yarn test`. DB-набор включается переменной
`PAGINATION_TEST_DATABASE_URL` и работает только во временной схеме.
